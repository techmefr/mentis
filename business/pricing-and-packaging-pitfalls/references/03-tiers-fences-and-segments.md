# pricing-and-packaging-pitfalls §3 — Tiers, fences and segments

A tier table is a set of fences. Each one has to stop someone for a reason, and each plan has to be built for
someone in particular.

## 3.1 One trigger per tier
1. **Every paid tier has one named event that makes the tier below hurt**: a limit reached, a teammate added,
   a capability needed. Write the event next to the tier.
2. **If you cannot name the event, the tier has no reason to exist.** "More advanced features" is copy, not a
   trigger.
3. **Check the trigger from the customer's side:** at the moment it fires, does moving up solve their problem?

## 3.2 What to gate
1. **Gate what separates casual from serious use**: volume, number of people, advanced control, access
   features, support level.
2. **Do not gate the capability that delivers the core value.** A buyer who cannot get the core outcome on
   the entry plan cannot judge the product and leaves.
3. **A fence must be explainable in one line** on the page.

## 3.3 Packaging anti-pattern checklist
Run these as questions on a draft tier table. The sources attached numeric cutoffs to them; those were
arbitrary and are not used here.
1. **A top tier that is a dump of roadmap items**, with no trigger of its own.
2. **A tier whose only difference is cosmetic**, a decoy that fools nobody.
3. **An entry tier whose cost to serve eats most of its price**, so staying there forever is a loss.
4. **Usage overage hidden inside a flat plan** (§2.3).
5. **A top tier with no published anchor** and no stated reason for not publishing one: buyers with a budget
   disqualify themselves unseen.
6. **The same feature in every tier at the same scope.** It is a base feature; drop it from the comparison or
   differentiate its scope (limited, metered, unlimited).
7. **A tier nobody should rationally pick**, because another tier gives more for little more. Check each tier
   has a buyer.

## 3.4 Segments before pricing
1. **Personas differ in what they will pay and what they need.** An aggregate across segments describes
   nobody.
2. **Name the segments first** (size of company, use case, sophistication, buying process), then map features
   and a metric to each.
3. **Run surveys, tiers and trials per segment**; report n per segment (§5).
4. **A plan is built for one segment.** If a plan is for everyone, write which segment pays for it.

**Never** read a tier table without asking, tier by tier: who is this for, and what makes them move up.
