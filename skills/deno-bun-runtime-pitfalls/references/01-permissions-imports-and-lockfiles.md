# deno-bun-runtime-pitfalls §1 — Permissions, imports and lockfiles

Source: own craft knowledge, with the points marked "Deno docs" or "Bun docs" checked on 2026-10-20 against the Deno documentation (MIT repository) and the Bun documentation (MIT; the runtime ships some LGPL components, which does not touch the documentation text), rewritten in our words, nothing copied. Flags and defaults are to be re-read in the documentation of the runtime version in use.

## 1.1 Deno's permission model
1. **Deno denies file, network, environment, subprocess and native-library access until a flag grants it.** Grant each flag with a scope: read and write limited to named directories, network limited to named hosts, environment limited to named variables. A bare grant covers everything of that kind. (Deno docs: refused operations throw a not-capable error, explicit deny flags override allow flags, and the allow-all flag turns the sandbox off entirely.)
2. **Symptom: a script that "needs all permissions to work".** Cause: someone added the allow-all flag during development and it shipped. Fix: run once with prompts, record what was requested, and replace the flag with the exact list. (Deno docs, security page re-read 2026-10-20: when no flag is given and the output is a terminal the runtime asks interactively, so a CI run with no terminal gets a refusal instead; a permission audit log was not found on that page, so the audit-output route stays unverified.)
3. **Permissions apply to the process, so a dependency inherits them** (Deno docs, security page: all code on the same thread shares one privilege level, modules cannot have different ones, and revoking a permission through the permissions API after start-up returns it to the prompt state and so narrows what later code reaches). A transitive package with network access can send what the process can read. Keep read scope away from secret directories and key files, and review which hosts the network scope allows.
4. **Subprocess and native-library permissions are near-equivalent to full access,** since the child process is not sandboxed. Do not grant them for code you do not control. (Deno docs: a subprocess runs outside the sandbox with its own permissions, and allowing the runtime's own executable lets a child start with everything allowed; write access to a directory holding an allowed executable lets a program overwrite it; native libraries run as machine code in the process and make system calls the permission layer does not see.)
5. **Check:** the production start command and the task definitions contain no allow-all flag, and each scoped flag has a reason you can state.

## 1.2 Bun has no permission model
1. **A Bun process runs with the user's full rights,** like Node. Do not assume a sandbox; use a container user, filesystem permissions, and network policy for isolation, as for Node.
2. **Scripts from dependencies can run at install time under the package manager's rules, which differ from npm's.** Check which install scripts the manager runs by default and which it blocks until trusted, and keep the trusted list short. (Bun docs, lifecycle page re-read 2026-10-20: dependency lifecycle scripts do not run unless the package is on a trusted list, whose approvals are recorded in the lockfile; a curated default list of popular npm packages is trusted, only for npm-registry sources, so file, link and git sources need an explicit entry; defining the list in the project file replaces the default one, so a package that still needs a script (an image or bundler binary, for instance) must be listed again, and an empty list trusts nothing; a flag, a config setting or an environment variable turns all scripts off. Deno docs, Node page: it does not run npm lifecycle scripts by default either, a package is allowed by name at install time, and a native binding may then be missing at run time.)
3. **Never run untrusted code on either runtime for convenience of the flags.** Isolation for hostile input is a container or a virtual machine, not a flag.

## 1.3 Imports, resolution and lockfiles
1. **Deno resolves URL, registry and package specifiers, and a mapping file can alias them.** Pin versions in every specifier or in the mapping, never "latest" or an unversioned URL; an unpinned remote import changes under you. (Deno docs: third-party specifiers carry a version, the project file's import mapping can hold a caret range, and an outdated-dependencies command lists and updates them; the project-file reference read 2026-10-20 adds that the lockfile is on by default, records exact versions and integrity hashes, can be switched off by setting the lock option to false, and has a frozen option that makes the runtime fail if any dependency would change. The supply-chain page re-read 2026-10-20 names the matching command-line flag for frozen mode, recommends it for CI and production, and mentions a dedicated CI install command in recent releases; it does not state the default of the lock setting.)
2. **Commit the lockfile and install from it in CI** (a frozen or locked install mode). Without that, the pipeline resolves new versions and a green local build turns red, or worse, ships different code. Neither runtime freezes by default: Bun's install page says it is not enabled automatically in CI and offers a dedicated CI command, and Deno's supply-chain page asks you to enable it for CI and production.
3. **A lockfile can be ignored by an option in the project file (lock set to false)** and possibly by a flag or environment setting (not confirmed). Confirm CI really reads it: change a dependency without updating the lockfile and see the install fail.
4. **Bun's lockfile format has changed between versions** (binary to text). Pin the Bun version in the project and CI so every environment reads and writes the same format. (Bun docs, lockfile and install pages re-read 2026-10-20: version 1.2 made the text lockfile the default; the old binary file is converted with a documented command and then deleted; the frozen-install flag installs exactly what the lockfile says and fails when the manifest and lockfile disagree on a package, but not for edits that keep every package at its locked version, and the production flag implies it; with no lockfile, install migrates from another manager's lockfile, trying a fixed order (npm shrinkwrap, npm lockfile, yarn, pnpm) and warning about each one it skips, so two lockfiles do not disagree silently there; the original lockfile is kept.)
5. **Do not mix package managers in one repository.** Two lockfiles disagree silently; keep one and delete the other.
6. **Module resolution rules differ from Node's (own guidance, unverified).** File extensions, directory indexes, conditional exports and type-only imports behave differently; a path that resolves in one runtime can fail in the other.
7. **Deno skips package versions published very recently** (supply-chain page, re-read 2026-10-20: a minimum dependency age, 24 hours by default in the release the page describes, set in the project file, by flag or in the npm configuration file, and disabled by zero). Symptom: a fix released an hour ago is not picked up and an install resolves an older version than the registry shows. Check the setting before debugging the resolver.

## 1.4 Tasks, workspaces and configuration
1. **Define tasks in the project file** so the permission flags and arguments live in one place and are reviewed, not retyped in shell history.
2. **For a monorepo,** use the runtime's workspace feature or a task runner, and pin versions per workspace; see `monorepo-task-graph-and-cache-pitfalls` for cache and task-graph issues.
3. **Read environment variables through one validated config module,** not scattered calls; on Deno the environment permission is then a short, named list.
4. **Keep type-checking in CI even if the runtime strips types.** A runtime that runs TypeScript by removing types does not check them.

## Checks
- No allow-all flag; each scope has a reason (§1.1).
- Isolation relies on the container or VM where code is untrusted (§1.2).
- Imports are pinned; the lockfile is enforced; one package manager (§1.3).
- Tasks hold the flags; type-checking runs in CI (§1.4).
