# § 5 — HTTP contracts: the OpenAPI description, problem details, retries, pages

> Section 5 of `skills/api-design`. Read it when the contract is an HTTP API described (or about to be
> described) in OpenAPI: the description is written or linted, an error body is chosen, a write has to be
> safe to retry, a collection gets a page, a rate limit is answered. It sits next to §1 (contract-first),
> §3 (extension) and §4 (the same questions for a protobuf wire). Stamped against sources read 2026-10-02
> (see `references/origin.md`). The OpenAPI versions read are 3.1 and 3.2 (3.2 keeps 3.1 documents valid
> unchanged and adds native tag hierarchy among other things); a project still on 3.0 reads point 2 as its
> migration note.

1. **The description is written before the code, kept in one place, and kept in source control from the first
   commit.** An OpenAPI description is a source file that drives generation, mocks, tests and documentation,
   not an export; the first reason to write it first is practical: far more APIs can be built in code than
   OpenAPI can describe, and a limit discovered after the fact is fixed by twisting the description to fit,
   which yields a description that is unintuitive and incomplete. Where the description is generated from
   code, commit one of the two as the source of truth and have CI fail when the other drifts; two copies of
   the same fact, one of them hand-edited, are how a newcomer ends up not knowing which one is live (§1.1,
   §1.10).
2. **State the OpenAPI version and read the rules of that version.** 3.1 made the Schema Object a full JSON
   Schema 2020-12 dialect and changed spellings that a 3.0 tool will misread without complaint: a nullable
   type is a type array including `null` (not a `nullable` flag); an exclusive bound is a number (not a
   boolean beside `minimum`); a schema's `example` becomes a list under `examples`; a binary body is
   described with `contentMediaType`/`contentEncoding` rather than `format: binary`/`base64`. A document
   whose version line says one thing and whose schemas say the other is accepted by some tools and
   mis-generated by the rest. When upgrading, change the version line and the schemas together, and run the
   linter between the two.
3. **Say required, nullable and absent separately, and give nullable and absent the same meaning unless the
   protocol forces otherwise.** A property can be required or not, and null or not; a property that is neither
   required nor nullable-forbidden can arrive as `{}` or as `{"x": null}`, and a contract that gives the two a
   different meaning ("not decided yet" versus "decided against") is read wrongly by every client library that
   cannot tell them apart. Model the third state with an explicit value or a small object. The one standard
   exception is JSON Merge Patch, where `null` means delete and absent means leave alone; a patch endpoint
   says so (§1.5). A boolean is never null; an empty collection is `[]`, not null.
4. **Reuse by reference, split by the URL hierarchy, tag everything.** The same schema written twice is two
   schemas by the next release: move repeated shapes into `components` and reference them. Split a large
   description along the natural path hierarchy (everything under `/users` together) and not further: many
   tiny files and one huge file both break some tool. Every operation carries a tag defined at the top level.
5. **Operation ids are unique, URL-safe and chosen on purpose.** Documentation sites use them as anchors and
   generators turn them into method names in the SDK; a generated name is a public name (§2.2), so rename it
   with the same care as a field. Every operation declares at least one success response; every path parameter
   is declared and every declared path parameter appears in the path; enum values are all of the declared
   type and none is duplicated; examples validate against their schema; the server list holds no placeholder
   host and no trailing slash. These are mechanical, which is why they belong in the linter and not in review.
6. **Lint the description in CI with a ruleset checked into the repo.** Extend the standard OpenAPI ruleset,
   then add the house rules as custom ones and set the severity deliberately: findings that mean "this
   document is wrong" (unique operation ids, valid examples, undeclared path parameters) fail the build;
   style findings warn. A rule that is switched off to get a branch through is a project decision recorded in
   the ruleset with a reason, not a local override. The unused-component rule reports false positives on a
   description that is a library for others; scope it, don't drop it.
7. **One error shape: problem details, with a stable `type`.** The standard media type is
   `application/problem+json` and its members are `type`, `status`, `title`, `detail`, `instance` plus
   extensions. `type` is the primary identifier consumers branch on: a stable absolute URI that ideally resolves
   to human documentation, never a relative one (it resolves differently from different resources), and
   defaulting to `about:blank` only when the status code alone says everything. `title` is the same for every
   occurrence of the type (apart from localisation); `detail` is for this occurrence and for telling the client
   how to correct the request, not for debugging; consumers never parse `detail`, they read extension members.
   `status` repeats the HTTP status and must equal it, because software in the middle may not understand the
   body. Clients ignore extension members they do not know, so adding one is compatible (§3.4).
8. **Mint a problem type only when a client can act on it.** A condition any resource could produce is already
   a status code (a 403 on a PUT needs no custom type). Validation failures are one type with a list
   extension, each entry carrying a message and a JSON Pointer to the offending part of the request, so a
   form can map them to fields (§1.8). When several unrelated problems occur, report the most relevant one;
   a catch-all batch type maps poorly to HTTP. A type's definition states its recommended status code and, if
   it applies, the `Retry-After` behaviour.
9. **Error bodies never carry stack traces or implementation detail.** The details given for a problem are as
   much a disclosure surface as any other response: no stack dump, no SQL, no internal host, no existence of a
   resource the caller may not know about. Log the detail server-side with a correlation id and return the id
   in `instance` or an extension.
10. **Specify every success and error response of every operation.** Errors are part of the interface (§2.10):
    the status codes, the problem types and what condition produces each, especially the conditions the client
    can avoid. Use the most specific official status code, answer a batch with a per-item result (207).
11. **Intermediaries never rewrite what the application said, and never answer for it.** A gateway or router
    that returns 404 for a missing route has made an authoritative statement about application resources that
    it was not entitled to make; a client reads 404 as "this thing does not exist" and acts on it. Routing
    failures are temporary server-side codes (502, 503 or 504), not client errors.
12. **Make writes retry-safe, and choose the mechanism knowingly.** Three patterns exist and they give
    different guarantees. A conditional key (`If-Match` with a version or hash) prevents lost updates and
    duplicate creation and works for PATCH. A secondary key (a unique client-chosen business key stored on the
    resource) prevents duplicate resources from independent clients on POST. An idempotency key (a header, kept
    temporarily with the stored response and a hash of the request) is the only one that returns the exact same
    response, and it does not prevent two clients from creating two resources. A repeat of a key with a
    different payload is rejected with 400. The resource write and the key record must commit together,
    otherwise a crash between them either loses the key or double-executes; that is the part that is hard to
    get right outside a single database.
13. **Paginate every collection from the first release, with an opaque cursor, and avoid the total.** Offset
    pages duplicate or skip rows when data changes between requests and cost more as the offset grows;
    cursor pages avoid both, at the price of no jump-to-page. The cursor is opaque: clients never inspect or
    build one, and it encodes the position, the direction and the filters it was issued for. A total count is
    expensive to compute on a large table and, once published, clients depend on it and it is hard to remove
    (§2.6); offer it only on request, for example through a `Prefer` directive. Adding pagination later is a
    breaking change (§4.31).
14. **Rate limits answer 429 with information the client can use.** `Retry-After` in seconds is enough for
    general load shedding and needs no notion of an account; the three `X-RateLimit` headers (limit,
    remaining, reset) fit APIs with per-client quotas and should then appear on every response, not only the
    429. State whether reset is a relative number of seconds or an epoch: the common usages disagree.
15. **URLs name things.** Plural nouns for collections, no verbs, kebab-case path segments, no trailing slash
    or empty segment, identifiers that survive being pasted in a URL. Nest a sub-resource only when its life
    cycle is coupled to its parent, and keep the nesting shallow: depth multiplies URL length and the number
    of identifiers each handler must validate. Pick one casing for properties and one for query parameters
    and apply it everywhere; which one is less important than there being one (§1.9).
16. **Every endpoint declares how it is protected, in the description.** A security scheme (a bearer or OAuth 2
    scheme) is defined once under the components and applied to the operations with the scopes each one needs,
    so the requirement is visible to the client author and to the linter, which can flag a requirement that
    names an undefined scheme. Scope names follow one convention across services; permissions are not invented
    per endpoint.
