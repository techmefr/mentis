# flutter-native-bridge-ffi §1 — Channels and Pigeon

Sources: the Flutter platform-channels page (repository text at the time of reading) and the Pigeon README,
package version 29.0.7, which declares a Dart SDK constraint of `^3.11.0`; both read 2026-10-08. Where a
point is our own guidance it says so.

## 1.1 Channel or generated bridge
1. **Prefer a generated, typed bridge to hand-matched channel strings.** The platform-channels page offers two
   routes, plain channels and Pigeon, and says Pigeon removes the need to match strings between host and
   client for message names and data types. A renamed key then fails at generation, not in front of a user.
2. **Plain channels remain reasonable for simple data or low-frequency exchange,** and are what the README
   points to when the plugin targets Windows or Linux (its "when to choose which model" list).
3. **Pigeon's native-interop mode (direct FFI and JNI calls) is marked experimental in the README.** It is
   for high-frequency messaging, large typed arrays or synchronous host calls; it supports Android, iOS and
   macOS only, needs external tools, and the task-queue annotation is an error with it. Do not choose it by
   default.
4. **On the web, use JavaScript interop** instead of channels (platform-channels page).
5. **One place, none in a widget.** Create each channel or generated API in one directory and inject it
   behind an interface, never inside a widget, repository or state holder (our guidance), so the boundary can
   be faked in tests and found by search.

## 1.2 The contract of generated code
1. **The definition file is declarations only and lives outside `lib/`;** the generated Dart goes into `lib/`
   and the generated host code into the platform project (README usage section).
2. **Both sides must be generated by the same Pigeon version.** The README says the channel code is an
   internal detail that may change without warning and is not treated as a breaking change, and that mixed
   versions have undefined behaviour including crashes.
3. **So never split generated code across packages** (the Dart half in an interface package, the host half in
   an implementation package), and never use Pigeon-generated types in a public API; the README calls both
   strongly discouraged.
4. **Never edit generated files.** The README says generated code changes freely between versions, so a hand
   edit does not survive an update. Change the definition and regenerate.
5. **A wire format shared across languages has one owner per side and changes on both sides in the same
   commit,** proven by a round-trip test (our guidance).

## 1.3 Threads
1. **A channel call from the platform side into Flutter is made on the platform's main thread** (on Android
   the UI thread; on iOS the main thread). A call from Flutter to the platform comes from the root isolate or
   from a background isolate registered for that root (the platform-channels page).
2. **A plugin or channel used from another isolate needs that isolate registered:** pass the root isolate
   token in and call the background-messenger initialiser first (the page's example).
3. **Platform-side handlers run on the main thread by default;** on Android a task queue moves one to a
   background thread, and Pigeon exposes this through a task-queue annotation for platform channels only
   (README). A handler that blocks (disk, network, a long computation) goes to a task queue or a thread of
   its own.
4. **Even though messages are asynchronous, a channel method must be invoked on the platform's main thread**
   as the page's note states; do not assume "async" means "any thread".

## 1.4 Replying and failing
1. **The native side replies exactly once.** Pigeon notes that a host method written as synchronous makes it
   simpler to always reply exactly once; an asynchronous one must complete its callback or coroutine on every
   path, including the error path.
2. **Native errors reach Dart as a platform exception.** In Kotlin and Swift, a thrown flutter-error or
   Pigeon error is caught and translated for synchronous and modern async methods; for callback-style methods
   the error is returned through the result callback (README). Custom details are carried by those error
   types. How Dart maps the exception to a user-facing failure is `flutter-conventions` §8.

## 1.5 What can cross
Channels and Pigeon use the standard message codec, which carries booleans, numbers, strings, byte buffers,
lists and maps (platform-channels page); Pigeon adds custom classes, nested types and enums. Anything else
needs a custom codec or conversion on one side. Keep the payload small and structured: a channel is not a
file transfer.
