# § 7 — Engine notes: MySQL/InnoDB and SQLite

> Section 7 of `skills/sql-conventions`. Read it when the engine is one of these two. PostgreSQL is the
> reference in the other sections; here is where the other engines differ in a way that changes the code.
> The first block applies to MySQL/InnoDB, the second to SQLite.

## MySQL / InnoDB

1. **The primary key is the table.** InnoDB stores rows in primary-key order, and every secondary index entry
   carries the primary key value. A narrow, monotonically increasing key (a 64-bit auto-increment) appends and
   keeps every secondary index small; a wide or random key (a random UUID) scatters inserts, splits pages and
   enlarges every index. If outside identifiers are needed, keep the surrogate integer as the key and put the
   UUID in a separate unique column, stored in the compact binary form and, if it is generated by the
   application, time-ordered. Auto-increment gaps are normal.
2. **Foreign keys and their index.** MySQL requires an index on the referencing columns and creates one
   automatically when none exists, unlike PostgreSQL (§2.4). Name the index yourself so a later migration can
   refer to it.
3. **Use the four-byte UTF-8 character set,** the full one, as the table and connection default; the older
   three-byte one cannot store all of Unicode and is retained only for compatibility. Choose the collation once
   per database and do not mix, since comparing columns of different collations fails or forces a conversion
   that defeats the index.
4. **The `TIMESTAMP` type has a limited range, ending in January 2038,** and converts to and from the session
   time zone; `DATETIME` has a wide range and does no conversion. Choose by what the value means, store the
   instant in UTC, and set the connection time zone explicitly.
5. **Keep the default strict SQL mode.** The default mode in current versions makes an invalid or truncated
   value an error instead of a warning and a silent change. A configuration that turns it off converts bugs
   into data corruption.
6. **The default isolation is repeatable read, with next-key locks.** A locking read or an update over a range
   locks the gaps as well as the rows, even a row that does not exist, so inserts into the gap block. A unique
   lookup on a unique index locks only the record. A predicate with no usable index scans and locks every row it
   examines, which looks like a table lock and is not (InnoDB does not escalate); the fix is the index. Lower
   the isolation to read committed per session only for a measured gap-lock problem, not globally (§4).
7. **Read the plan with `EXPLAIN` and watch for three signs:** a full scan access type, a file sort, and a
   temporary table. `EXPLAIN ANALYZE` (in the 8.x manual) runs the statement and gives actual timings; the same
   caution as §3.2 applies. A non-sargable predicate, an implicit conversion or an `OR` across different
   columns usually explains the scan.
8. **Handle the deadlock error by retrying.** The deadlock error number is the signal to roll back and
   re-run the whole transaction after a short, growing pause (§4.3, §4.6). Look at the engine status output for
   the latest detected deadlock to see which statements and which order collided.
9. **Online DDL needs the clauses** (§5.5); an index added to a table with a heavy write load may need a
   shadow-table tool.

## SQLite

1. **Foreign keys are off by default and the setting is per connection.** Without turning enforcement on, every
   connection silently accepts violations. Enable it on each connection when it opens, in the one place that
   opens connections, and test that a violation fails.
2. **Typing is flexible by default.** A column's declared type is an affinity, not a rule, so a text value can
   land in an integer column. Declare tables strict (the `STRICT` table option) to have the declared type
   enforced; a strict table allows only a short list of types, so check that list against what you store.
3. **Use write-ahead logging for concurrent access,** where readers do not block the writer and the writer does
   not block readers. It needs all processes on the same host and does not work over a network filesystem; the
   database then has companion files that must travel with it for a backup to be valid. There is still only one
   writer at a time.
4. **Set a busy timeout on every connection.** A second writer gets a "busy" error immediately by default. The
   timeout makes it wait and retry; it replaces any handler set earlier on that connection, so set it once, in
   the connection-opening code.
5. **Start a transaction that will write as an immediate transaction.** The default deferred transaction starts
   as a reader, and its first write upgrades it; if another connection has written meanwhile, the upgrade fails
   with the busy error even though a timeout is set, because waiting cannot make a stale snapshot current. An
   immediate transaction takes the write position at the start, where waiting is useful.
6. **A single file is not a server.** It suits an embedded store, a local tool, a test fixture and a
   read-mostly dataset. A workload with many concurrent writers, or needing network access, wants a client-server
   engine; deciding that late is a migration.
