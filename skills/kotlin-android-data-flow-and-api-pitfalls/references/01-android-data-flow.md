# kotlin-android-data-flow-and-api-pitfalls §1 — Android data flow

Source: the Architecture Learning Journey document and the agent guide of the Now in Android app (Apache-2.0,
commit a49ed25, read 2026-10-16), rewritten. It describes one reference app's choices, so each point is a
default to follow unless the project states another.

## 1.1 Layers and direction
1. **Three layers: data, an optional domain layer and UI.** Higher layers react to changes in lower ones; events
   flow down and data flows up, carried by Kotlin flows.
2. **The guide's own warning: this is the official Android architecture, not "clean architecture"**, so concepts
   from the other style may not apply or may apply differently.
3. **The domain layer holds use cases**: classes with one invocable method that combine and transform repository
   data and remove duplicated logic from view models. In the reference app it has no event-handling use cases;
   the UI calls repositories directly for events.

## 1.2 Repositories
1. **A repository is the only way to reach its data**, and each repository has its own models.
2. **Reads are streams, not snapshots**, because a snapshot may be stale by the time it is used. Every client
   must be ready to react to change.
3. **Writes are suspend functions and the caller scopes their execution.**
4. **Local storage is the source of truth and reads from it are not expected to fail.** Errors belong to
   reconciliation with the remote source.
5. **Database models stay internal to the data layer**; the repository maps them to the public model that other
   layers consume, as an intermediate step on the stream.

## 1.3 Sync
1. **Fetch remote data, write it straight to local storage, and let the stream from local storage update the
   listeners.** That keeps read and write concerns from interfering.
2. **Reconciliation is a background job with exponential backoff**, delegated to the platform work scheduler
   through a worker that implements a small synchronizer interface; enqueue it at app start.
3. **Different data sources suit different data**: a relational database for related records, a typed
   preferences store for user choices, a network source for remote JSON.

## 1.4 UI state
1. **Model screen state as a sealed hierarchy of interfaces and immutable data classes**, emitted only through the
   transformation of data streams, so the state always reflects the underlying data and the UI handles every
   possible state (the guide's example has a loading state and a success state).
2. **A view model combines or maps the cold flows from use cases and repositories into one flow of UI state, then
   converts it to a state flow** so the UI can read the last known state.
3. **User actions are plain method calls on the view model, passed to the UI as lambdas** (a "follow topic"
   lambda in the guide's example); the view model forwards them to the repository.

## 1.5 Tests and CI notes from the agent guide
1. **Local tests use the coroutines library, a flow-testing library and an assertion library; UI tests use the
   Compose test rule with a component activity**, and larger tests live in the app module.
2. **Screenshot tests are generated by CI, so a workstation does not commit them.**
3. **Build variants are named flavours and build types**, and the guide gives one fix command for formatting.
   The commands are project-specific; do not copy them to another project.
