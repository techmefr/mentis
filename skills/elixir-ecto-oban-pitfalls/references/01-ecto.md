# elixir-ecto-oban-pitfalls §1 — Ecto

Sources: the Ecto 3.14.2 documentation in `lib/ecto/changeset.ex` and `lib/ecto/repo.ex`, read 2026-10-08.

## 1.1 Uniqueness
1. **The guarantee is a unique index plus `unique_constraint/3`.** The constraint hands the database's violation back as
   a changeset error: define the unique index in a migration, name the same fields in the changeset, and set the
   constraint name explicitly when the index name cannot be inferred (composite indexes, partitions).
2. **`unsafe_validate_unique/4` is early feedback only.** Its documentation says it has race conditions: two
   submissions can both pass the check and both insert. It does not replace `unique_constraint/3`, and constraints
   are only checked when all validations pass, which is why the early check is useful for most conflicts.

## 1.2 Upserts
1. **`on_conflict: :nothing` returns `{:ok, struct}` that does not reflect the database.** If the primary key is
   generated by the database, the struct's key is `nil` when nothing was inserted (`ignored.id` is `nil`). Do not read
   the id from that struct to link records; fetch the row.
2. **An update-style `on_conflict` needs `:conflict_target` on PostgreSQL,** and the columns named must carry a
   unique index. When the application generates the id, or when `on_conflict` is an update, the database does not
   say whether an insert or an update happened, so the result alone cannot tell you.
3. **A read then an insert is not an upsert.** Doing a lookup before inserting is two statements with a gap; use
   `on_conflict` with `:conflict_target` so the database decides atomically (own guidance, from the same facts).
4. **`insert_all` does not fill generated values.** Primary keys of types other than `:id` and `:binary_id`, and
   timestamps, are not autogenerated by it; set them explicitly. The documentation says this is by design, the same
   as for `update_all`.
5. **`{:unsafe_fragment, ...}` passes SQL without sanitising it.** It is available for `:conflict_target` and
   `:returning`; the documentation says it is not escaped. Never build the fragment from user input.

## 1.3 Transactions
1. **A failed statement aborts the whole transaction in the database.** An insert that violates a unique constraint
   fails and every later operation in the same transaction raises (in PostgreSQL, error 25P02, "current transaction
   is aborted"). That holds even when your code handled the `{:error, changeset}`: the next `Repo.insert` still
   raises.
2. **The documentation gives two ways out:** pass `mode: :savepoint` to the statement that can fail, so the
   transaction rolls back to the savepoint and carries on, or handle the failure outside the transaction by
   letting the `{:error, _}` end it and recording the failure afterwards. A changeset that is invalid before it reaches the database sends no statement, and does not abort anything.
3. **`Repo.transact/2` exists in 3.14.2 and `Repo.transaction/2` is deprecated in its favour.** `transact`'s
   function returns `{:ok, value}` or `{:error, reason}`; an `{:error, _}` return rolls back, and a raised
   exception rolls back and bubbles up. The function may take no argument or one, in which case it receives the
   repo of the transaction (confirmed in the documentation of the development branch). Use `transact` in new code.
4. **A transaction belongs to one process.** A process started inside it uses a separate connection and is not
   part of the transaction. In tests with the SQL sandbox, sharing the parent's connection with a child that the
   parent is waiting on can deadlock.
5. **A nested `transact` call is not a second transaction.** Called inside another transaction, the function is
   simply run in the outer one. If the inner call fails, even when its error is rescued, or rolls back, the whole outer
   transaction is aborted and nothing is committed, as the `Repo.transact/2` documentation states. A helper that opens
   its own `transact` and is reused inside a caller's therefore cannot fail alone: return its error to the caller,
   or give the statement that may fail `mode: :savepoint` (point 3.2).
