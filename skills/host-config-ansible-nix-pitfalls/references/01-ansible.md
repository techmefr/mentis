# host-config-ansible-nix-pitfalls §1 — Ansible

Source: own craft knowledge, with the points marked "Ansible docs" checked on 2026-10-20 against the official Ansible documentation pages (variables, handlers, error handling, check mode, strategies, YAML syntax, FAQ, shell and file modules) and two pages of the linter's rule set, read for facts only and rewritten in our words; their licence was not verified. Module and keyword behaviour is to be re-read in the documentation of the version in use.

## 1.1 Idempotence
1. **A task states a desired state and reports a change only when it made one.** Prefer the module for the job (package, file, template, service, user, line-in-file) over a shell or command task.
2. **Symptom: the second run still shows changes, or a run is never "green".** Cause: a shell or command task with no way to detect "already done". Fix: add a creation or existence guard, or a real changed-when condition, or replace it with a module. (Shell module page, re-read 2026-10-20: it makes no idempotence claim, it supports check mode only partially, and its creates and removes options skip the step when a named file exists or is absent; the docs prefer the command module unless a shell is really needed. The linter's changed-when rule says the same from the other side: command-running modules do not detect changes themselves, so give them a changed-when expression or a creates or removes argument, handlers included.)
3. **Use a template or a copy for whole files and a line edit only for a single line you do not own.** Repeated line edits drift into a file nobody can read; one template under version control is the single source.
4. **Declare the end state, not the steps.** "Package present" survives a re-run; "run the installer" does not.
5. **Check:** run the playbook twice on a clean test host. The second run must report zero changes; any change is a defect to explain.
6. **Quote every variable you pass into a shell task with the quote filter.** The shell module page warns that unsanitised values let a semicolon or similar input run extra commands. Symptom: a host name or file name with a space or a metacharacter breaks the task or runs something else. Check: grep shell tasks for a bare templated variable.

## 1.2 Variables and inventory
1. **Variable precedence has many layers and the winner is rarely the one you expect.** Keep a setting in one place by default (role defaults), override it in one documented layer (group or host variables), and do not use the highest-priority layers casually. (Ansible docs, variables page re-read 2026-10-20: role defaults sit near the bottom of the precedence list and extra variables on the command line always win; defining each variable in one place is the documented way to avoid reasoning about precedence, shared defaults go in the all-hosts group file, and the role's variables file ranks much higher than its defaults, though role parameters and extra variables can still override it; passing values as parameters when calling a role shows the intent in the playbook.)
2. **Prefix role variables with the role name** so two roles do not share a name and overwrite each other (own guidance; the docs read advise passing role variables as parameters for clarity).
3. **Keep environments as separate inventories with their own group variables,** not one inventory with conditions; a production host must not be reachable from a staging run by a typo.
4. **Facts are collected from the host and can be stale or missing** when fact gathering is off. Do not branch on a fact you did not gather in this run.
5. **Quote values that must stay strings;** the YAML parser turns an unquoted `no`, `on`, `1.10` or a leading zero into other types, a classic source of a wrong file mode or version. (Ansible docs, YAML syntax and variables pages re-read 2026-10-20: quote values YAML would convert, such as yes, False and version numbers like 1.0 (read as floats); quote a value that starts with a template expression or a brace, since the parser reads it as a dictionary; quote values containing a colon followed by a space or a space then a hash; lowercase true and false are the recommended boolean spelling, for the linter's default settings. File module page, re-read 2026-10-20: quote octal modes so Ansible receives a string and converts it itself; an unquoted value with a leading zero sometimes works and can fail in loops; any other unquoted number is taken as decimal and gives wrong permissions.)

## 1.3 Secrets and access
1. **Encrypt secret variables with the tool's vault feature or an external secret store** and keep the vault password out of the repository. A plain-text secret in a variable file is a leaked secret once the repository is shared.
2. **Stop secrets reaching logs.** Mark tasks that handle them with the no-log option, since task output and verbose runs print arguments. (Ansible docs: the option hides a task's command and results in verbose output, apply it to single tasks rather than whole plays because play-wide use makes debugging hard, and it does not hide what the engine's own debug mode prints; the same page says plaintext passwords do not belong in playbooks or host variables and points to the encrypted-variables feature.)
3. **Write secret files with restrictive owner and mode in the same task that creates them,** so there is no window where they are world-readable.
4. **Use a dedicated connection user with the least privilege escalation it needs,** and keys, not passwords. Pin or verify host keys instead of disabling host-key checking.
5. **Do not put a secret in a command line:** other users on the host see it in the process list. Pass it through a file with a restrictive mode or an environment of the task.

## 1.4 Check mode, diff and testing
1. **Run in check mode with diff and read the output before the real run.** Check mode is a prediction: tasks that depend on earlier changes, or shell tasks, may be skipped or wrong in it. (Ansible docs, check-mode page re-read 2026-10-20: a module without check support reports nothing and does nothing; a condition on a result registered by an earlier task has no meaningful value in check mode; a task can force or forbid check mode per task, and a variable tells a task it is running in check mode; the diff flag works alone or with check, is most useful with file-templating modules, is best run on one host at a time, and can be turned off per task when the content is sensitive. The page does not say shell tasks are skipped by default, and does not say whether the no-log option hides diffs.)
2. **Test roles on a throwaway host or container** and make that test part of the review; a role tested only on the author's machine meets the real host first in production.
3. **Lint the playbooks in CI** and treat the linter's rule on shell tasks and unnamed tasks as a gate (own guidance for the gate itself; the linter's rule pages say every task should have a name, for readable output and logs, and that command-running tasks need a changed-when; the linter's index page says its rules are opinionated and can be disabled one by one, and does not cover CI use).
4. **Name every task** in plain words; the run output is the log you read at night, and an unnamed task is unreadable there.

## 1.5 Handlers, ordering and rollout
1. **A handler runs once at the end, after the tasks that notified it, only if they changed something.** A failure before the end means the handler never ran and the service keeps the old configuration; force handlers or restart explicitly when the order matters. (Ansible docs, handlers and error-handling pages re-read 2026-10-20: a handler runs once at the end of the play, in the order handlers are defined, only when a notifying task reported a change (a looped task counts as changed if any item changed), and a flush step runs those notified so far; if a later task fails on a host the notified handler does not run there unless the force option is set in the play, in the configuration or on the command line, and a forced handler still does not run on a host that became unreachable. Handler names are templated early, so a missing variable in a name can fail the play; put variables in task parameters instead.)
2. **A restart that breaks the service ends the run on that host.** Validate the new configuration file with the service's own check command before replacing the old one.
3. **Roll out in batches with a failure threshold** so a bad change stops after one host, not the whole fleet. (Ansible docs, strategies and error-handling pages re-read 2026-10-20: the batch keyword takes a number, a percentage or a list of growing sizes, scopes failures to the batch, and a percentage always gives at least one host; the maximum-failure percentage applies per batch and must be exceeded, not just reached, so with a batch of ten and 30 percent, a fourth failure aborts, and a value of 50 with a batch of four does not stop at two failures; the any-errors-fatal setting finishes the failing task on the batch then stops the play on all hosts.)
4. **Never change the way you reach the host (SSH settings, firewall, network interface) in the same run without a safeguard.** Keep a second path or schedule a revert.
5. **Keep tasks free of assumptions about the first run.** A host that was partly configured by hand must converge to the same state; tasks that fail on existing state are not idempotent.
6. **The ignore-errors keyword does not cover every failure.** The error-handling page says it applies only when a task runs and reports a failure: an undefined variable, a connection problem, a missing package or a syntax error still stop the play. Symptom: a play that was meant to tolerate a failure aborts anyway. Fix: handle the specific case with a failed-when condition or a rescue block.

## Checks
- Modules over shell; a second run reports no changes (§1.1).
- Variables in one layer each; environments separate (§1.2).
- Secrets encrypted, kept out of logs and command lines (§1.3).
- A diff run was read; roles tested on a throwaway host (§1.4).
- Config validated before restart; batched rollout; access path protected (§1.5).
