# vue-nuxt-vuetify-conventions §6 — i18n

> Section 6 of `skills/vue-nuxt-vuetify-conventions`. Read it when any string the user will read. The other sections and the guardrails stay in `SKILL.md`.

1. **Locale files flat, no nested objects**: nesting makes a key impossible to grep and invites two keys
   for one string. Once a key is only reachable by walking a tree, nobody can answer "is this sentence
   already translated somewhere" without reading the whole file, so they add it again.
2. **Keys are the full source sentence in the source language, lowercase** — in the source-language file,
   key and value are identical. A key like `err.42` tells a translator nothing, and it hides the second
   failure too: when a key is missing, the fallback renders the key, so a sentence-key degrades into the
   right sentence in the wrong language while `err.42` degrades into garbage on screen.
3. **Domain-specific strings live with the domain that owns them** (its own `lang/` folder, merged at
   runtime); only genuinely transverse strings — navigation, shared buttons, generic errors used by more
   than one feature — go in the central file. A central file that grows with every feature becomes the
   file every branch conflicts on.
4. **An i18n label inside a list or a config is a `computed`**, never frozen at `setup()` time: a label
   read once does not follow a locale change. The same applies to table headers, validation messages,
   chart legends, select options and anything cached in a store — the symptom is a page that switches
   language except for the four labels that were built eagerly.
5. **Page title and subtitle metadata are translated too.** A `definePageMeta`-style title left as a raw
   string is the page that stays in the wrong language, and it is also the string that shows up in the
   browser tab and in a shared link, so it is the most visible one to miss.
6. **No user-visible text hardcoded in a component.** Where a project has no i18n layer at all, the text
   still comes from one place, not from wherever it was first typed — that is what makes adding a
   language later a configuration change instead of an audit.
7. **Plurals go through the library's plural mechanism, never through `n > 1`.** A ternary encodes the
   assumption that there are two forms; Russian and Polish have three, Arabic six, and several languages
   treat zero as its own case. The hand-rolled version is correct in the source language and wrong
   everywhere it matters, which is exactly the bug nobody on the team can see.
8. **Never build a sentence by concatenating fragments.** Word order is not universal: a "deleted" label
   glued to a count glued to an "items" label cannot be translated into a language that puts the verb
   last, because the translator receives three pieces and no sentence. Interpolate named parameters into
   one whole string instead, and keep the punctuation inside it.
9. **An interpolated value stays data.** Don't put markup in a translation and don't render a translation
   as HTML: the locale file is edited by people outside the code review, so a translation rendered as
   HTML is an injection surface with a friendly name. Where a fragment genuinely needs styling, pass it
   through the library's component interpolation rather than through `v-html`.
10. **Dates, numbers and currencies go through the locale formatter.** Decimal separators, thousands
    separators, date order and currency placement all differ, and a hand-formatted `dd/mm/yyyy` reads as
    the wrong day to half the world. The display timezone is a decision too — pick it explicitly and say
    which one the user is seeing, because the default is the browser's and that is rarely what a business
    report means.
11. **Assume a translation is longer than the source.** German runs roughly a third longer than English,
    and a button sized to fit its French label truncates the moment the locale changes. Let text wrap,
    avoid fixed widths on anything holding a sentence, and check one long locale before shipping the
    layout.
12. **A missing key is loud in development and safe in production.** Falling back silently to an empty
    string is the worst option: the label simply disappears and nobody notices for a release. Warn at
    build or in the console during development, fall back to the source language at runtime.
13. **One key per meaning, not per occurrence — and never one key for two meanings.** Reuse follows
    meaning, not spelling: "Close" the verb on a button and "Close" as an adjective on a status are one
    word in English and two different words nearly everywhere else. Sharing that key produces a sentence
    that is wrong in a way no English-speaking reviewer will ever see.
14. **Text baked into an image or a generated chart is text nobody can translate.** If a label has to be
    in the picture, the picture becomes per-locale, which is a maintenance cost worth avoiding — render
    the label in the DOM over the image instead.
15. **The source-language file is part of the change, in the same commit as the code.** A string added in
    a component and forgotten in the locale file ships as a raw key on screen; there is no build error to
    catch it, so the discipline is the whole mechanism.
