# nestjs-node-conventions §4 — Prisma: schema, migrations, data access

> Section 4 of `skills/nestjs-node-conventions`. Read it when a schema, a migration or a repository is written. The other sections and the guardrails stay in `SKILL.md`.

1. One repository per business aggregate (`UsersRepository`), injected into the service like any other Nest
   provider: the service never knows `PrismaClient` directly, only the repository.
2. Every change to `schema.prisma` goes through a committed migration (`prisma migrate dev`), never through
   a manual change to the schema in the database.
3. Type-safe operations: rely on the types generated by Prisma (`Prisma.UserCreateInput`,
   `Prisma.UserWhereInput`...) rather than retyping a query's inputs/outputs by hand.
4. Prisma mapped types (`Prisma.UserGetPayload<{ include: {...} }>`) to type precisely the result of a
   query with relations, rather than an approximate homemade type or an `any` on the repository's return.
5. Type guards on the models when a relation is optional (conditional `include`): check the relation is
   present before reading it, never a cast that hides the `undefined` case.
6. For any Prisma integration point not covered here (middleware, seeding, multiple connections...), refer to
   the official Prisma documentation rather than guessing. Transactions and the connection lifecycle are
   below; they follow the framework's Prisma chapter (NestJS 12 documentation, Prisma ORM 7), read 2026-10-02.
7. **Expose the client through one provider in a dedicated module** that exports it. Providers are singletons,
   so every importing module shares one client and one connection pool; the repositories of rule 1 sit on it.
   Marking that module global is a trade-off the framework documents; prefer explicit imports in a modular
   application.
8. **Connect at startup and disconnect on shutdown through the lifecycle hooks.** The client connects lazily on
   the first query; connecting in `onModuleInit()` makes a misconfigured connection fail at boot, not on the
   first request. Disconnect in `onModuleDestroy()`, which also disposes the driver adapter and closes its
   pool. That hook runs on `app.close()`, and on a termination signal only when shutdown hooks are enabled
   (`references/06-config-lifecycle.md` §6). The old `beforeExit` event is not supported in ORM 7.
9. **Read the connection URL through the configuration service with a throwing getter**, so a missing value
   stops the application at startup (`references/06-config-lifecycle.md` §1).
10. **Keep the ORM's major and its CLI on the same major.** The framework's chapter warns that the package
    registry's `latest` tag can point to a pre-release of a different CLI; install the major deliberately.
    Version-dependent details (driver adapter required, config file name) are Prisma ORM 7's.
11. **A transaction is a decision at the use-case level.** Three forms exist: nested writes (one query, atomic
    by itself), an array of queries passed to `$transaction()` (run in order in one transaction), and an
    interactive transaction (an async function: commit when it resolves, roll back when it throws).
    Everything meant to be atomic goes through the transaction client the function receives; a query sent
    through the outer client runs outside it. Options: `maxWait`, `timeout`, `isolationLevel`.
12. **Do not thread the transaction client through every method signature** when several services take part:
    it couples them. Either keep the whole unit of work inside one repository method, or hold the active
    transaction in async local storage (the framework points to the community `nestjs-cls` transactional
    plugin with a Prisma adapter) so repositories pick it up without a parameter. Keep a transaction short: no
    network call to a third party inside it.
