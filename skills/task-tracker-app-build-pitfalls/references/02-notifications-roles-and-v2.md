# task-tracker-app-build-pitfalls §2 — Notifications, roles, recurrence and v2 regrets

> Part 2 of `skills/task-tracker-app-build-pitfalls`. Read it when notifications, permissions, an import or the
> first release are planned. Mostly craft knowledge; point 1 carries a fact from the code in `references/origin.md` (source 1), read 2026-10-20. Everything not marked as sourced is our own guidance.

1. **Notifications come from events, with a matrix.** Symptom: people are notified of things they caused, or
   miss the one that matters. Fix: write a matrix of event (assigned, mentioned, status changed, comment added,
   due soon, blocker cleared) against recipient (assignee, creator, watchers, mentioned user) and channel
   (in-app, email, push); never notify the actor of their own action; every send goes through the notification
   layer (see `skills/laravel-mail-via-notifications`). The reference tracker lets each user choose a notification filter (all tasks, only those assigned to me, only those created by me, or both) and a set of projects, and its recipient query accepts a user id to exclude (source 1).
2. **Coalesce, then send.** Symptom: one edit session produces six emails, or a bulk move sends hundreds.
   Check: change five fields on a task in a minute and bulk-move fifty tasks. Fix: emit one event per user
   action, not per field; delay sending a short window and merge events on the same task; a bulk operation
   sends one summary; offer an immediate, a digest (hourly or daily) and an off setting per event type; keep
   an unread inbox in the app as the source and email as a copy.
3. **Reassignment and removal move notifications too.** Symptom: the old assignee keeps receiving updates, or a
   removed member still gets mail about a project. Fix: on reassignment, drop the old assignee from implicit
   watchers unless they chose to watch; on removal from a project, delete their watches and invalidate pending
   notifications and links.
4. **Visibility is enforced where the data is read.** Symptom: a link in an email opens a task the recipient
   can no longer see, or the search shows titles of private projects. Fix: membership and role checked in the
   list query, the search index, the export, the notification link and the attachment URL; an unauthorised
   link returns the same response as a missing one (see `skills/field-and-row-permission-ui-api-pitfalls`).
5. **Roles are abilities per project.** Symptom: "member" can delete the project or change the workflow. Fix:
   abilities such as view, comment, edit task, manage members, manage workflow, delete project, mapped to a few
   roles per project, plus a workspace-level role for admins (see `skills/laravel-permissions-not-roles`).
   Guests and clients get a restricted role with no internal comments and no other project names.
6. **Internal and external comments are separate.** A comment visible to a client project guest needs an
   explicit flag; the default is internal, and notifications to guests carry only external comments.
7. **Recurring tasks are a rule that creates instances.** Symptom: completing a recurring task rewrites it, or
   a missed run creates a pile of overdue copies. Fix: a recurrence rule stored apart from the task, an
   instance generated by a scheduled job that is idempotent (see `skills/laravel-idempotent-jobs`), a stated
   policy for skipped periods (create one, create none, catch up with a cap), the rule evaluated in the owner's
   zone with the daylight-saving behaviour decided, and each instance linking to its rule so "stop repeating"
   is one change.
8. **Reminders are jobs that re-check state.** A due-soon reminder queued yesterday must check at send time that
   the task is still open, still assigned to this user and not snoozed; otherwise it nags about finished work.
9. **Imports and integrations are idempotent and staged.** Symptom: re-running a CSV or a sync duplicates tasks,
   or a webhook replay reopens a closed one. Fix: staging with preview, an external id per row as the key,
   counts of create, update, skip and conflict before commit, the import id on created rows for undo, status
   mapping chosen by the user from the source's labels to this workflow's categories (see
   `skills/csv-xlsx-import-export-pitfalls`), and outbound events carrying an id and a version so receivers
   ignore replays. Git and chat links are references to external records, not copies.
10. **Search and filters have defined meaning.** "Mine" means assigned to me and open by category; "overdue"
    uses the point 11 function from §1; saved views store a filter definition, not ids (see
    `skills/filters-search-and-saved-views-pitfalls`). A counter on a screen and the list it opens must use the
    same query.
11. **Time tracking and estimates are separate from status.** Estimates, logged time and remaining effort are
    their own rows with an author and a date; totals are queries, not a second editable number on the task.
12. **What to split first.** Build in this order and keep each independent: projects, memberships and tenancy;
    tasks with a workflow and history; assignment and comments; ordering; dependencies; roles and visibility;
    notifications; recurrence, imports and integrations; then time tracking and reports. Ship the first three
    before any board or calendar view, because every view reads that data.
13. **What is regretted at v2.** Free-text statuses; no category so reports read labels; dense integer
    positions; no cycle check; one assignee column that later needed many; due dates with no zone rule;
    notifications per field; hard-deleted tasks with history; role names checked in screens; no tenant column;
    an import with no external id. Each is cheap at the first migration and expensive after data exists.
14. **Laravel and Nuxt pointers, short.** In Laravel: a workflow and transition table with an action class that
    checks it, a sortable position column with a rebalance job, a database transaction plus row lock around
    the dependency insert, notifications batched through a queued job, a scheduled idempotent job for
    recurrence, and policies per project role. In Nuxt: keep filters in the URL, reconcile optimistic moves
    against the server's returned state, never rely on the front to hide data, and treat exports as a download
    from the API.
