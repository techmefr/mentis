# laravel-conventions §13 — Safe migrations on a live database

> Section 13 of `skills/laravel-conventions`. Read it when a migration touches a table that already holds
> data in production, renames or drops something, adds an index or a constraint, or backfills. The column
> and enum rules are §3; the multi-release strategy for retiring an old shape is `skills/deprecation-migration`;
> this section is what a single migration file must do so a deploy does not take the site down or lose rows.
> The other sections and the guardrails stay in `SKILL.md`.

1. **Read the SQL before it runs.** The pretend mode prints the statements a migration would execute without
   executing them. Reading them is how a "simple" column change is seen to be a table rewrite, and how a
   statement that differs between the local engine and the production one gets caught. For a destructive or
   large change the output goes in the merge request description.
2. **The old code and the new schema run together during a deploy.** A rolling or two-step release means the
   previous version of the application serves requests against the schema the migration just produced, or
   the new version runs against the old one. A migration is therefore written so that both versions work
   between its start and the moment the last server is replaced; a change that cannot be compatible is split
   across two releases.
3. **Rename and drop are expand and contract, never one step.** Add the new column or table, deploy code
   that writes both, backfill, deploy code that reads the new one, and only in a later release remove the
   old (`skills/deprecation-migration`). A direct rename breaks the still-running old code at the second the
   migration commits; a drop is irreversible except from backup.
4. **Know what the statement locks.** On a large table an `ALTER` can block writes, or all access, for its
   whole duration, and the lock queue behind it stalls every request. Look up the behaviour for the engine
   and version in use: some additions are instant or online, some rewrite the table. Where the engine
   supports an online algorithm or a non-blocking index build, use it; on engines where a lock timeout can be
   set for the session, set one, so the migration fails fast instead of queuing the site behind itself.
5. **Concurrent index builds cannot run inside a transaction.** Where the engine builds an index without
   blocking writes, the statement is refused inside a transaction block; the migration declares that it
   does not run within one, and is then not atomic, so it has to be safe to run again after a partial
   failure (point 12).
6. **A constraint can fail against existing data, so look at the data first.** A unique index fails on
   duplicates, a foreign key fails on orphans, a `NOT NULL` fails on nulls, a check constraint fails on rows
   it forbids. Query for the offending rows before writing the migration, decide what happens to them
   (merge, delete, correct) in a data step of its own, and only then add the constraint (§3, point 27 for the
   nullability ordering).
7. **A backfill is not a migration.** Updating millions of rows inside the schema migration holds a
   transaction open and the locks with it. Add the column and the code that fills it for new rows in the
   migration, and populate old rows with a command that works in id-ordered chunks, commits per chunk, can be
   stopped and resumed, and is safe to run twice (`skills/laravel-idempotent-data-commands`). Run it as a
   deploy step with its progress visible.
8. **Migrations do not use the application's models.** A model is the current shape of the code; a migration
   is a frozen step in history. Once the model gains a cast, a scope, an event listener or a renamed column,
   an old migration that used it fails on a fresh database or does something different on it. Use the query
   builder, or a minimal anonymous model declared in the migration file.
9. **`down()` is real or honestly absent.** A rollback that has never been run is not a rollback. Write it
   to restore the structure, run it once in CI against the migration it reverses, and where the change
   destroyed data say so by making the method throw a clear exception instead of recreating empty columns. The
   actual recovery plan for a destructive migration is a restore from a backup taken, and test-restored,
   before the deploy.
10. **An applied migration is never edited.** Anyone who has run it keeps the old schema and is now wrong
    without a signal. A correction is a new migration. The only edit tolerated is before the migration
    reaches a shared branch, and the squashed schema dump (§3, point 38) is regenerated by a person who
    understands what it replaces.
11. **Two paths are tested: from nothing, and from the last release.** CI migrates an empty database to the
    current schema, and migrates a database restored at the previous release's schema (with realistic data
    volume if the change is heavy) forward. The first catches a migration that only works incrementally; the
    second catches one that only works on an empty table, the failure that passes in CI and breaks in
    production (§3, point 27).
12. **A migration that can stop halfway can be run again.** Where the engine cannot make a statement atomic
    with the schema change, guard each step on the current state (the column exists, the index exists) so a
    second run completes the work instead of failing on the part that was already done.
13. **Concurrent runs are prevented.** When several instances start at once and each runs migrations, the
    isolated option takes a lock so one runs and the others wait or skip. Without it two processes race on
    the migration table and on the schema.
14. **Time the migration on production-sized data.** A change that takes twenty milliseconds on a
    development database can take twenty minutes on the real table. The duration on a restored copy is the
    figure the release plan uses to decide between an ordinary deploy, an off-peak window and the two-release
    split of point 2.
15. **Defaults and generated values on a big table are decided deliberately.** Adding a column with a
    default may be instant on one engine version and a full rewrite on another; a computed default (a
    function result, a per-row value) is usually a rewrite. When in doubt add the column nullable without a
    default and fill it with the point 7 command.
16. **Reference data inserted by a migration is idempotent and keyed on a natural key** (§9, point 10), so
    running the sequence on a database that already holds it adds nothing and changes nothing.
