# when-stuck §6 — The unblock card

> Section 6 of `skills/when-stuck`. Read it when the stuck item is a task that is too vague or too big to start
> ("work on the pricing", "do something about onboarding") and the person or the agent cannot say what the first
> move is. 🟡: rewritten from documentation, not yet run on a real stall.

**Which kind of stuck this is.** Not a failing approach (§1 to §5) and not missing information only a human has
(that one is a question, asked at once). The task is not yet concrete enough to have a first step. The method is
two things only: the output, then the next physical action.

1. **Ask for the output as a noun.** "When this is done, what exists that does not exist now?" A document, a sent
   message, a deployed change, a decision. A feeling ("feel sure about the migration") is not an output; a thing is
   ("a one-page proposal with three options"). If the answer is fuzzy, sharpen it once, and do not loop.
2. **Cut it to what fits in a day.** If the output is bigger than that, ask which piece can be finished today:
   a completable slice that can be checked off tonight, not "start working on it". If it already fits, skip this.
3. **Ask for the first physical action, as a verb and an object.** "Open the layout file and sketch the header",
   "draft the message to the client", "create `release-notes.md` and write its three headings". "Think about it" and
   "research" are not actions; ask for the one inside them (where, and what would be typed).
4. **Ask whether it is the best use of the time, not whether it is a good idea.** Most ideas are worth
   something; the useful question is whether something better is being avoided. One question: if the answer is
   a confident yes, go; if it hesitates, spend one exchange on it and then go.
5. **Write the result as a card.** Four lines, plain text:

   ```
   Output: the concrete deliverable
   Today's slice: the part that fits in a day (the output itself when it already fits)
   Next action: verb and object, the literal first step
   Safe to try: one line saying why this is good enough to start
   ```
6. **Keep it short.** Two or three exchanges, not ten. When the person's first message already answers a
   question, skip it; when the slice and the action are already clear, write the card at once. No motivational
   padding.
7. **The card is not a spec.** If the output turns out to be a feature, the card ends here and the work goes
   through the spec-kit cycle (`CONVENTIONS.md` Rule E); the card is the way to a first step, not a requirement.
   It lives in the conversation or the task's trail, never as a document of its own.
